# Dotty Tutor 产品路线图

> 本文只回答“学生和内容生产者先获得什么能力”。技术实现顺序请看
> [`engineering-roadmap.md`](engineering-roadmap.md)，运行治理细节请看
> [`runtime-governance-plan.md`](runtime-governance-plan.md)。

## 产品定位

Dotty Tutor 是一个本地优先的学习项目，验证“教材/错题输入 → 结构化互动内容 → 学生作答 → 错题陪练 →
掌握验证 → 复习”的学习闭环。当前只聚焦中文教材和初中数学，不追求一次覆盖所有学段和商业化场景。

### 服务对象：先按一个学科组来设计（2026-08-29）

此前路线图没有写明“做给谁”，结果学生端、内容生产端和错题端三面等权重推进，每一面都在各自加功能。
现在明确：**主用户是老师，最小服务单元是一个学科组**（例：初中数学组，5～8 位老师、约 300 名学生）。

选这个单元而不是“一所学校”或“一个学生”的理由：

- 备课组长可以自己决定试用，不必走学校采购流程；一个学期就能看到效果。
- 300 名学生的作答量足以让掌握度分布有统计意义；单人 Demo 的样本量不足以验证“学习是否有效”。
- 老师不缺题（有教辅、有历年卷），缺的是“这 45 个人里谁在哪个知识点上卡住了”。这件事人工做不到——
  批 45 份作业只能知道对错，得不到分布和归因。而掌握度、错因分类、变式验证这三件本项目已经做完了，
  只是当前全部朝向学生，没有一个朝向老师。

由此产生的四面权重调整：

| 面 | 此前 | 现在 |
| --- | --- | --- |
| 内容生产端 `/studio` | 与另两面等权重 | **核心能力**：老师把校本讲义/试卷变成可发布题目 |
| 学生端 `/learn` | 自选已发布试卷 | **作业执行面**：显示被指派的作业，而不是可任选的发布列表 |
| 错题端 `/mistakes` | 拍照录入为主入口 | **自动产物**：作业做错的题自动入错题本；拍照降为课外题的补充入口 |
| 老师视图 | 不存在 | **新增**：班级知识点掌握分布，老师侧的主界面 |

`/mistakes` 的功能不缩减，变的只是入口。拍照录入要求学生有自驱力，而这恰恰是目标用户欠缺的；
作业产生的错题是零操作成本的。

### 方向 ≠ 部署（两件事分开推进）

“服务对象是学科组”是**产品方向**判断，它决定做哪些功能；它**不等于**现在就要做私有化部署。
下面这组仍然明确暂缓，直到出现第一个真实试用的学科组：

- 登录鉴权、多租户 `org_id` 隔离、行级权限
- 三角色（org_admin / teacher / student）的权限体系与管理后台
- 私有化部署所需的备份、监控、限流和现场可运维性

理由：`org_id` 晚做确实要付一次迁移成本（估约一周），但给一个尚未验证的产品形态提前铺多租户，
是为可能不存在的客户付钱。当前用现有 `learner_id` 顶着即可——班级和作业指派在单机单库下同样跑得通，
而它们才是验证形态所必需的那一部分。

## 当前版本：MVP

已具备：

- 内容生产端可以上传教材、识别题目、生成互动试卷并经过结构质量门禁后发布。
- 学生端可以消费已发布试卷，完成选择、多选、判断、填空、数值、简答和画线等题型。
- 错题可以进入陪练线程，获得分层提示、变式验证和掌握度记录。
- 支持错题本、进阶本和 1/3/7 天复习任务的本地演示闭环。

## 当前执行顺序（2026-08）

产品路线按“先保证学生能完成任务，再证明学习有效，最后扩展表现形式”排序。当前 MVP 的主链路已经
跑通，因此后续不再并行堆叠新题型或新模型，按下面顺序推进：

1. **P0 收口：稳定演示闭环**（已完成）
   - 学生作答、重新提交、完成态、错题归档和陪练验证必须可恢复。
   - 生产端失败题必须可定位、可修复、可重新审核，不能把错误内容发布给学生。
2. **P1 证据闭环：让“学会了”可解释**（当前优先）
   - 完善错误原因 → 变式策略 → 验证结果 → 掌握度 → 1/3/7 天复习的证据链。
   - **最小闭环已落地**：自动错题先等待学生确认 `errorReason`；每次变式验证追加保存作答和 `EvaluationEvidence`；单题 Evidence API 与进度页已展示验证正确率、复习完成率和同知识点再错率。动态间隔、双归因和多轮重新掌握仍不在本轮范围。
   - **前置：知识点实体化与掌握度重构已完成**（见 [`engineering-roadmap.md`](engineering-roadmap.md)
     的 T0 收口项）。当前掌握度按发布版本内每道题的最新证据派生；跨教材身份和更复杂教学法仍需真实场景
     验证后再扩展。
   - 补充学习效果指标和典型学生路径回归，先用脱敏本地数据验证，不建设数据平台。
   - **教学法层（T0 完成后接着做，四条是一组）**：
     - *分类型复习间隔*：当前 1/3/7 天对所有知识点一刀切。记忆型该密集、设计型该稀疏，
       且答对连续两次应加速、答错应回退。固定间隔不响应表现，本质上不是间隔重复。
     - *定量 / 定性双门槛*：记忆型与程序型用准确率卡（如 ≥0.9）；概念型与设计型很少存在
       可字符串匹配的标准答案，应改为让学生讲一遍、由陪练判定通过。当前 7 种题型共用一套
       `{correct, partial, incorrect}`，用准确率衡量概念理解本身就不成立。
     - *推进由掌握度算出，而不是阶段计数器*：没过门槛就一直停在同一个目标；已证明掌握的
       直接跳过（test-out）。这是“掌握式学习”与“按顺序刷课”的分界，也同时提供了
       “卡住的过不去”和“会了的跳过去”两个能力。
     - *错因双归因*：`mistake_items.error_reason` 目前是单字段。拆成“学生自评归因”与
       “AI 判断归因”两个字段——先让学生自己判断再看 AI 怎么说，这是元认知训练的关键动作，
       合并成一个字段就丢掉了两者的差异信号。
       **位置已就位（2026-08-30）**：自评动作已从确认表单迁到陪练首轮，学生先判断再看分析；
       剩下的是把单字段拆成两个字段。注意跳过自评时不写入任何值——`unknown`（完全不会）是
       一种真实自评，与“没有回答”含义不同，混为一谈会污染出题策略。
3. **P1 老师视图：把已有数据转向老师**（新增 2026-08-29）
   - 作业指派（`class` + `assignment` 两张表）：学生端从“自选发布”变成“今天的作业”。
     这一个概念决定产品是自学工具还是教学工具，是形态验证的核心，且不需要多租户即可实现。
   - 班级知识点掌握分布看板：纯展示层，读掌握度数据，不新增模型能力。
   - 掌握度喂回出题：老师布置作业时，把该班已有的掌握度和错因分布输入生成 prompt，
     让模型显式说明这次避开了什么、补了哪些弱项。数据已经在库里（`mastery_states`），
     但当前出题链路完全没有读它——这是同一份数据的另一个出口，接一根线就是“个性化出题”。
     **依赖 T0**：口径不对时喂回去只会放大错误。
   - 验收标准是**能不能拿给一位真实老师看懂、并让他说出“有用/没用”**，而不是页面做完。
     形态可以先用模拟数据做出来判断，不必等真实数据齐备。
4. **P1 工程质量：让 AI 修改可比较、可回放**
   - **第一版已完成**：建立 OCR/公式/题图/讲解 Badcase 集、确定性回放和 Judge 报告比较；后续持续扩充样本。
   - 每次模型、Prompt、Schema 或校验器修改都比较正确率、结构质量、耗时和调用次数。
5. **P2 表现实验：提升互动和内容表现**
   - 只在前两项稳定后，选择一个互动数学库，随后再评估动画、Lottie、TTS 缓存和教材检索。
6. **暂缓生产化**
   - 登录鉴权、多租户隔离、商业化和高可用服务仍不是下一步；班级与作业指派已上移到 P1，
     它们在单机单库下实现，不含租户隔离和权限体系（区别见上文“方向 ≠ 部署”）。

产品需求进入开发前，必须先写清用户验收；技术实现顺序统一参见
[`engineering-roadmap.md`](engineering-roadmap.md)，避免把产品目标和基础设施任务混在同一张清单中。

## P0：稳定当前演示闭环

完成标准：学生可以连续完成一套题；内容生产者可以得到可展示的题目；失败时有明确反馈，不会无限等待。

- [x] 学生提交正确答案后稳定进入下一道未完成题；最后一道题进入完成态，也可以回看已完成题目。
  （2026-08-30 修正：答对后的“回答正确”反馈曾被切题 effect 在同一帧清空，学生实际看不到正反馈。
  现在停留 1.2 秒再推进，期间可点“继续下一题”跳过等待。）
- [x] 已提交题目保留答案和结果，刷新或返回后按钮显示“重新提交”。
- [x] 错题陪练完成态能够进入验证；验证只需要一道题，答错可以重新提交。
- [x] 学生做题时不主动请求 TTS 或讲解，只有主动求助时才产生反馈。
- [x] 错题归档不删除作答和学习证据；归档会清理旧陪练线程和消息，恢复后重新创建线程。
- [x] 题干、选项、条件、讲解和历史消息中的公式、图片、Markdown 图片保持一致显示，并有内容生产端与学生端 Playwright 回归覆盖。
- [x] 内容生产端支持单题修复和整套重新审核，并清楚显示实际生成/审核模型、运行 ID 与修订号。
- [x] 生成、审核、陪练和 OCR 模型选择相互独立，学生端不暴露内容生产配置。

本轮已完成：内容生产端的单题修订版本、批次重生成、重新 OCR 和整套重新审核均返回不可变审计证据；OpenAPI 类型生成与校验已接入。

- [x] PDF 上传完成后自动排队生成整本试卷，失败批次不阻塞其它题目并可回看完整结果；已有任务仍支持补跑整套试卷。
- [x] 界面不再泄漏内部实现：删除路线图阶段徽章（`PHASE 04`）、面向学生解释架构边界的说明块、
  掌握度置信度等评估字段，以及全站 21 处装饰性英文 eyebrow。（2026-08-30）
- [x] `/studio` 首屏让位给主任务：4 个模型/OCR 选择器收进默认折叠抽屉，发布状态机从顶栏

- [x] 学生试卷页信息去重：题号只由新增的题号进度条承载（四态、可点击跳题），

## 已论证但未排期（2026-08-29）

以下条目来自一次与同类开源产品（DeepTutor）的架构对照，产品价值已经想清楚，**但都还缺一个真实的
触发信号**。写在这里是为了不重复论证，不是为了排期——任何一条进入队列前必须先满足自己的触发条件。
这与本路线图对渲染通道、多小问的处理方式一致：先建证据，让真实信号决定动手时机。

- **仿真卷（照一份卷子出同构新题）**：老师上传一份期中卷，用已抽取的题型分布、难度梯度和知识点
  覆盖当模板，生成若干套同构模拟卷。OCR、题目抽取和质量门禁都已具备，缺的只是“把抽取结果当模板
  复用”这一步。在 To B 语境下价值不低——找/编模拟题是老师最高频的动作之一。
  > 触发条件：第一个试用学科组明确提出“我要照这份卷子再出几套”。在此之前不做，它是新功能，
  > 会挤占 T0 和 P1 老师视图。

- **出题结果增量发射**：每生成完一道题就推送一次、前端立刻渲染卡片，而不是整批跑完才出结果。
  当前 `/studio` 是批次处理，老师要等整批完成。
  > 触发条件：出现真实的“等太久”反馈，或整卷生成端到端耗时的 P95 超过可接受阈值。
  > 当前没有测过这个数——先在批次任务上记录耗时分布，用数据决定，不要凭“流式体验更好”排期。

- **按内容类型固定的内容块模板**：把“一节课的内容长什么样”固化成数据（讲解 N 字 → 图示 →
  练习 M 题 → 闪卡 K 张），按内容类型（推导 / 练习 / 史料）各备一套，再配一个深度旋钮统一缩放
  篇幅（预习和考前突击要的不是同一个东西）。`lesson_documents.blocks_json` 已经是块结构，
  缺的是生成侧的模板层。
  > 触发条件：P1 老师视图跑通，且老师反馈“题够了，但缺讲解”。属于 P2 内容表现，不与 P1 并行。

- **教材原文的定位与注释模型**：locator 语法（`12` / `12-14` / `3,12,17`）+ 注释带
  locator/quote/offset 并可回跳原文，让讲解和错题锚到教材页码，而不是只关联一个知识点字符串。
  > 触发条件：出现“教材原文并排阅读”的形态需求。当前学生端不展示教材原文，这套模型没有落点。

- **知识点依赖图**：T0 让知识点成为实体之后，再给它加前置关系边（A 依赖 B / A 扩展 B）。
  有了图才能回答“这题错了 → 该退回去补哪个前置知识点”，而不只是“这个知识点弱”。
  关键判断：**边不必让模型猜**——教材有目录树、有课标知识点体系、有章节前后关系，
  从教材结构直接导出的依赖图，准确率和 LLM 生成的不在一个量级。这是“内容是审定教材”
  相对“内容是任意文档”的结构性优势，值得用足。
  > 触发条件：T0 完成、且 P1 老师视图上线后老师追问“那他该回去补什么”。
  > 在此之前知识点扁平列表已经够用。

- **教材版本漂移检测**：教材重新 OCR、换版次或修订之后，已生成并发布的题目会与新原文脱节。
  可以对教材源文件算确定性指纹并快照到发布记录上，之后比对，把受影响的发布标记为“已过时”。
  指纹函数 `pdf_content_hash()` 已经有了（当前只用于 OCR 缓存键，不是数据库列），
  缺的是给 `lesson_publications` 加一列存快照并做一次比对。
  > 触发条件：出现第一次“同一本教材换了版本重新导入”。单人 Demo 阶段不会发生，
  > 但一个学科组同时用同一本书时迟早发生。

- **拍照录题改单次多模态调用**：如果当前是“检测题目区域 → OCR → 结构化 → 校验”的多步流水线，
  值得测一次“单次多模态调用 + 仅在产出不可用时触发一次修复”能不能打平。多阶段视觉流水线每一步
  都在丢信息，且延迟差一个量级；参考实现正是把四阶段收缩成一次调用后接口不变。
  > 触发条件：先测一组对照（准确率 / 延迟 / 成本），数据打平或更好才改。不测不改。

- **题图的视觉复审闭环**：生成 → 渲染 → 让视觉模型看一眼 → 不合格进修复循环。
  `evaluation/judge.py` 已经在做文本侧的 judge，这是视觉侧的对应物，适用于题图、画线题图形和插图。
  > 触发条件：Badcase 语料里出现成规模的“图渲染出来但不对”样本。当前主要坏样本是切分和归属，
  > 不是渲染质量。

- **生成前先审形状 + 成本估算**：当前 `/studio` 的审校在生成之后，返工成本高。可以改成先出
  “这批要生成什么形状”的提案让老师确认，并在确认前给出预计耗时（估算从生成模板本身推导，
  不另写一套，才不会与实际漂移）。
  > 触发条件：与“出题增量发射”共用一个信号——先把整卷生成的端到端耗时分布测出来。

- **朗读前剥除 Markdown / LaTeX 标记**：教材内容里 Markdown 和公式很多，直接送 TTS 会念出
  星号井号。一个纯函数的量级。
  > 触发条件：随下一次动 TTS 通道时顺路做，不单独立项。

**明确不采纳**：把出题改成“探索 → 规划 → 逐题生成”的三阶段代理流水线。
`apps/api/domain/questions/pipeline.py` 已有自己的生成与质量门禁链路，且当前没有任何一个失败模式
指向“缺少探索阶段”。换架构要有待解决的问题，不能因为另一个项目这么做。

同样不采纳：**图片 / 视频生成能力**（文生图、文生视频的 submit → poll → download 适配层）。
当前没有任何产品需求指向它；等真要做“讲解视频”时再评估，届时注意这类服务需要三个独立超时
（单次 HTTP、整体渲染、轮询间隔），只设一个总超时会把网络抖动和渲染慢混为一谈。

## 明确暂缓

- A Level 多学科题库。
- 商业化会员、支付、多租户隔离、登录鉴权和教师运营后台。
  （班级与作业指派已进入 P1，但只在单机单库下实现，不含租户隔离与角色权限——见“方向 ≠ 部署”。）
- 7×24 SLA、高可用、弹性扩缩容和完整公网运营体系。
- Multi-Agent、LangChain、LangGraph 等全局代理编排。

## 产品验收原则

1. 先验证学生是否能完成任务，再增加模型或页面能力。
2. 任何 AI 功能都必须有确定性状态机、错误回退和可重复测试。
3. 新题型、新动画或新模型必须是独立实验，不阻塞现有错题和复习闭环。
