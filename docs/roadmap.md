# 路线图与生产边界

Dotty Tutor 当前是本地优先的 MVP。核心教材数字化、互动辅导和 AI 错题陪练闭环已经可用，覆盖
拍照录入、多轮陪练、掌握验证和 1/3/7 天复习，但尚未达到匿名公网服务所需的安全性、隔离性和
可运维性。

## 路线图使用方式

路线图已拆成产品路线和技术路线，避免“用户要什么”和“系统怎么实现”互相覆盖：

- **产品优先级**：见 [`product-roadmap.md`](product-roadmap.md)，只记录用户价值、产品阶段和产品验收。
- **技术优先级**：见 [`engineering-roadmap.md`](engineering-roadmap.md)，只记录正确性、质量、性能和基础设施。
- **详细设计**：见 [`runtime-governance-plan.md`](runtime-governance-plan.md) 和
  [`mistake-coach-plan.md`](mistake-coach-plan.md)。

本文件保留历史阶段和已完成记录，迁移期间不再在此新增技术任务；后续执行状态以两份新路线图为准。

## 当前限制

- API 没有登录、授权、用户、班级或租户隔离。
- OCR、PDF 完成和模型调用仍在 HTTP 请求内同步执行。
- 模型/OCR 选择和部分读取缓存属于单个 FastAPI 进程。
- PDF、Markdown 和题图仍保存在本地文件系统。
- 生成阶段会对结构失败的单题自动修复两次；仍失败的题在发布时自动隔离，整套无合格题时安全阻断。
- 单页快速导入没有进入完整审校和持久化流水线。
- 选择题和简答题没有统一的确定性答案引擎。
- 前端当前最多展示 5 道题。
- 数据库表由 `create_all()` 初始化，尚无 Alembic 迁移历史。
- 已有结构化日志和请求 ID，但尚无集中式指标、追踪、错误监控和自动备份。
- 错题章节和知识点目前由模型建议、学生确认，尚未关联版本化教材知识树。
- 错题陪练已实现对话线程、受约束状态机、按错误原因生成的变式验证、进阶本迁移和 1/3/7 天复习进度闭环。

## 代理编排框架决策

当前阶段继续保持简单明了：**暂不引入 LangChain、LangGraph 等代理编排框架**。现有流程由
FastAPI 路由、领域服务、Runtime/Store 和明确的状态机组成，已经能够覆盖教材处理、题目生成、
错题陪练和掌握验证；直接增加框架会引入额外抽象、依赖和调试成本，不会为个人技术 Demo 带来
足够的收益。

后续只有在确实出现以下信号时，才评估局部引入，而不是一次性改造成全局框架：

- 多个代理需要并行、串行、条件分支和人工审批，并且流程难以用当前领域服务表达。
- 需要跨请求恢复长流程，持久化每个节点的输入输出，并支持暂停、重试、取消和幂等恢复。
- 同一套工具调用、上下文裁剪、状态检查和失败回退逻辑在两个以上业务流程中重复出现。
- 现有状态机、任务队列和可观测性已经无法清晰解释或稳定测试代理执行路径。

达到触发条件后，先用一个独立的领域服务或实验模块验证收益，限定在复杂多轮陪练或后台任务
编排边界内；保留现有 Runtime 接口和结构化事件作为应用边界，避免让页面、数据库模型和普通
API 依赖框架对象。评估结果至少记录流程可读性、恢复能力、测试成本、运行时开销和依赖维护
成本，确认收益后再决定是否扩大使用范围。

## 下一阶段：AI 运行治理与后台任务

下一阶段借鉴通用 Agent Platform 的运行快照、Model Gateway、Job Store 和事件模型，但继续保持模块化
单体，不建设独立控制平面。详细设计、验收标准和 PR 边界见
[AI 运行治理与后台任务演进计划](runtime-governance-plan.md)。

建议按以下顺序执行，当前均为规划项：

1. [ ] 创建不可变 `RunSnapshot`，固定每次运行的生成模型、审核模型、OCR、提示词和校验器版本。
2. [ ] 让 `run_id` 贯穿 OCR、生成、审校、发布和日志，并统一稳定的运行事件名。
3. [ ] 复用 PostgreSQL `upload_jobs` 建立 Job Store，以单个 Worker 执行 PDF/OCR/批量生成长任务。
4. [ ] 增加取消、有限重试、租约恢复和幂等发布，不因 Worker 重启重复生成或丢失进度。
5. [ ] 建立脱敏离线评测集，持续测量 OCR、切题、公式、质量门禁、陪练判定、耗时和调用次数。
6. [ ] 在指标稳定后统一 `ModelRequest` / `ModelResult`，让模型回退策略显式、可追踪。

Redis、OpenTelemetry、LangGraph 和 MCP 都属于按信号升级项，不是完成上述计划的前置依赖。

## 前端知识表达与互动技术选型

这部分路线服务于“知识动画 + 结构化内容 + 互动学习”，作为学习项目采用渐进式选型，不以堆叠技术名词为目标。
当前项目已经使用 React、结构化 `LessonDocument`/`LessonBlock`、`rendererRegistry`、KaTeX/`MathText`、
Canvas/SVG 和错题掌握闭环。新增能力必须先复用这些边界，不能为不同入口再复制一套题目或课程渲染器。

### 当前已采用

- [x] 使用 KaTeX 和统一 `MathText` 处理题干、选项、题目条件、讲解和历史 LaTeX 兼容。
- [x] 使用结构化课程块连接题目、讲解、提示、公式、图形和 TTS，而不是把整节课保存为一段 HTML。
- [x] 使用 React 组件、Canvas/SVG 和 Renderer Registry 支撑选择题、判断题、画线题和分步讲解。
- [x] 使用错题本、变式题、掌握验证和 1/3/7 天复习任务实现 Khan/Duolingo 式学习闭环的基础版本。

### 第一阶段：稳定内容模型和互动渲染边界

- [ ] 在 `frontend/src/types/lesson.ts` 和 `backend/lesson_contracts.py` 明确 `markdown`、`formula`、`diagram`、
  `interactive-math`、`quiz`、`animation` 内容块的版本化契约。
- [ ] 新增 `InteractiveMathCanvas` 渲染边界；页面只组合它，不直接依赖具体绘图库。
- [ ] 为每种内容块补充 MathText、图片、键盘输入、画布动作和错误回退的 Playwright 回归案例。
- [ ] 在文档中记录“Canvas 负责图形，HTML/MathText 负责公式文字”的边界，避免公式重新回到 `fillText` 路径。

验收标准：同一份 LessonBlock 可以在内容生产端预览和学生端消费；新增渲染器不修改题目业务状态；公式、图片和
交互状态在刷新后仍有明确的恢复或丢弃策略。

### 第二阶段：选择一个互动数学库做小范围实验

只选择一种，不同时引入 Mafs、JSXGraph 和 Desmos：

- [ ] 函数图像、坐标系、滑块和参数探索：评估 Mafs，限定在 `interactive-math` 实验题型。
- [ ] 点、线、圆、拖拽几何构造和证明：评估 JSXGraph，限定在几何题 Renderer。
- [ ] 只有在确实需要外部计算器体验且能接受外部运行时依赖时，才评估 Desmos API。

评估记录至少包括：React 集成复杂度、无障碍能力、移动端触控、导出/回放、许可证、包体积、离线运行和与现有
题目答案契约的适配成本。实验成功后只保留一个库，并通过 `InteractiveMathCanvas` 隔离；实验失败则回退到现有
Canvas/SVG，不影响其他题型。

### 第三阶段：动画生产与反馈动效

- [ ] 需要批量生成稳定视频时，评估 Manim 作为服务端/Worker 离线渲染器，前端使用 `<video>` 加字幕和暂停点。
- [ ] 需要浏览器内实时改变参数时，评估 Motion Canvas；不与 Manim 同时作为同一条生产链路的必选依赖。
- [ ] 答题反馈、连续学习和掌握升级动效稳定后，再评估 Lottie；仅用于表现层，不承载学习状态。
- [ ] 只有出现视频生成耗时影响接口时，才把动画渲染迁移到后台任务和对象存储。

### 暂不引入

- [ ] MathJax：当前 KaTeX 已统一且性能更适合题目列表；只有遇到 KaTeX 不支持的教材公式时再做局部评估。
- [ ] MDX/unified：当前模型生成内容以 JSON 契约为主；人工课程创作需求出现后再作为离线内容生产格式。
- [ ] Khan Perseus：借鉴其 Widget、答案契约和渐进提示设计，不直接替换现有题目系统。
- [ ] LangChain、LangGraph 和多智能体：继续遵循“出现复杂跨请求编排信号后局部评估”的决策。

建议拆分为独立 PR：`refactor/lesson-block-contracts`、`feature/interactive-math-canvas`、
`experiment/mafs-renderer` 或 `experiment/jsxgraph-renderer`、`chore/animation-worker`。每个实验都必须
可单独回滚，不能与登录、试卷发布或掌握度迁移混在一起。

## 学生端与内容生产端边界

- `/studio`：内容生产者上传教材、选择 OCR/模型、生成和预览互动内容。
- `/learn`：学生消费已发布内容，进入个人错题本和掌握复习，不提供整本 PDF 上传或模型配置。
- `/mistakes`：学生空间下的单题错题录入与陪练；保留拍摄单道错题，不承担教材生产。
- `/textbooks`：仅作为旧版本兼容地址跳转到 `/studio`。

## 错题陪练交付顺序

错题产品以“录入一题—陪练—验证掌握”为最小闭环，完整决策见
[AI 错题陪练产品规划](mistake-coach-plan.md)。

1. **角色入口（已完成）**：`/studio` 承载内容生产，`/learn` 汇总学生学习能力，`/mistakes` 承载错题闭环。
2. **录入与确认（已完成）**：单题 OCR、裁切、人工修正、章节知识点建议和错误原因。
3. **有状态陪练（已完成）**：一题一线程、结构化作答、上下文摘要和多轮提示。
4. **掌握验证（已完成）**：完成一道验证题并答对后进入进阶本；答错可在原题上重新提交。
5. **复习（已完成）与移动端**：已有 1/3/7 天复习任务；微信内浏览器与弱网体验仍待验证。

第一版只聚焦初中数学，不同时扩展全部学段、实时视频、教师后台和多智能体。

## 暂缓范围：A Level 多学科与生产级服务

为保持个人学习项目的边界清晰，以下方向暂不纳入当前开发、验收和版本发布：

- **A Level 多学科题库**：暂不扩展 A Level 数学、物理、化学等学科，也不建设跨学科课程内容。当前只验证
  中文教材/初中数学的 OCR、结构化题目、错题陪练和掌握复习闭环。等现有闭环稳定，并且准备好真实的学科
  数据集和评测集后，再单独规划学科扩展。
- **生产级服务能力**：暂不建设多租户登录、教师/班级权限、7×24 SLA、高可用与弹性扩缩容、集中式监控、
  计费、合规审计和公网运营能力。异步任务、对象存储、配额、认证等内容仍保留在后续 P0/P1 规划中，
  但不阻塞本地 Demo 的学习和演示。

当前优先级仍是：单题体验、题目/公式/图片质量、陪练状态机、掌握验证、复习闭环和可重复测试。

## 后续优化重点：AI 质量与学习数据闭环

这组任务是当前个人技术 Demo 最值得继续投入的方向。目标不是增加更多 Agent，而是让每次模型或规则
调整都能被复现、评估、定位和回滚，并能证明学生是否真的学会。它们依赖运行快照和稳定事件，按以下顺序推进。

### Q1：离线评测与 LLM-as-Judge

- [ ] 建立脱敏金标准集，覆盖 OCR、公式、题目切分、题图归属、七类题型和陪练对话。
- [ ] 同时保留确定性指标和评分模型：答案正确性、结构质量由代码判定；讲解清晰度、是否针对误区等
  主观质量由独立审核模型按固定 rubric 评分。
- [ ] 每次模型、Prompt、Schema 或校验器变更前后自动回放，生成可比较的基线报告。
- [ ] 审核模型记录版本、评分依据和置信度，不能让同一个生成结果无依据地自我通过。

### Q2：Badcase 回放与回归闭环

- [ ] 统一 Badcase 标签：OCR 丢字、公式损坏、选项/题图错位、答案错误、讲解不符、重复提示、阶段越权、
  超时和错误回退。
- [ ] 保存脱敏输入、`run_id`、模型/Prompt 版本、失败阶段和人工结论，不保存无边界聊天历史或密钥。
- [ ] 支持从 Badcase 重放，并比较修复前后的结构结果、评分、耗时和调用次数。
- [ ] 修复后的样本自动进入回归集；未达到质量门槛时禁止把对应模型或 Prompt 设为默认。

### Q3：学习效果漏斗与成本指标

- [ ] 统一记录“错题确认 → 开始陪练 → 完成原题纠错 → 完成验证 → 1/3/7 天复习”的业务事件。
- [ ] 展示错题确认率、陪练完成率、首次有效提示率、验证正确率、复习完成率和同知识点再次出错率。
- [ ] 同时记录每轮模型耗时、调用次数、回退率和估算成本；不把学生原文和答案写入普通指标日志。
- [ ] 第一版使用 PostgreSQL 聚合和本地报告，不提前引入独立数据平台或埋点 SaaS。

### Q4：轻量教材检索实验

- [ ] 仅针对已审核的教材片段、概念和例题，按 `knowledgePoint` 检索少量带来源证据。
- [ ] 检索结果必须带来源和置信度；证据不足时回退到普通陪练，不编造教材引用。
- [ ] 先使用 PostgreSQL 元数据过滤和全文检索；只有离线评测证明需要语义召回后，再评估向量数据库。
- [ ] RAG 只辅助讲解，不覆盖确定性判题、掌握度和状态迁移。

建议拆分为可单独验证和回滚的 PR：
`test/offline-ai-evaluation`、`feature/badcase-replay-loop`、
`feature/learning-funnel-metrics`、`experiment/textbook-retrieval`。

## 可借鉴的 AI 教育工程机制

同类项目的工作流和模型目录提供了几项值得学习的工程经验。这里记录的是可迁移的机制，
不是照搬对方的模型清单、批量规模或运营参数。所有实现仍需通过本项目的离线评测和本地演示验证。

### Q5：陪练上下文分层与 Prefix Cache

- [ ] 将陪练请求拆成稳定前缀和动态后缀：稳定前缀包含系统规则、工具定义、题目/知识点上下文、
  Schema 和教学阶段规则；动态后缀只包含学生最新输入、最近消息和状态变化。
- [ ] 记录稳定前缀 token、动态 token、总耗时、调用次数和实际 Provider，先建立基线再判断缓存收益。
- [ ] 仅在模型 Provider 明确支持 Prefix Cache 时启用缓存；缓存键必须包含模型、Prompt、Schema、
  题目版本和知识点版本，学生答案和个性化诊断不得跨线程复用。
- [ ] 上下文摘要压缩后必须更新版本号，避免旧摘要与新题目或新状态混用。

建议分支：`perf/tutor-prefix-context`。这项优化服务于陪练延迟和成本，不改变领域状态机的判定权。

### Q6：教材 OCR 预检与脏页报告

- [ ] 在正式 OCR 前对每页做轻量预检，识别空白页、目录/出版信息页、疑似题目页、无图页、公式密集页和
  图文混排页，并保存页面类型与原因。
- [ ] 为每本教材生成预检摘要：总页数、可处理页数、疑似脏页数、无图页数、需要视觉 OCR 的页数和抽样结果。
- [ ] 预检结果只决定路由和提示，不直接删除页面；页面级质量门禁、局部重试和人工修正仍是最终保障。
- [ ] 将脏页样本、OCR 失败原因和修复结果进入 Badcase 回放集，形成教材质量回归报告。

建议分支：`feat/ocr-preflight-report`。先支持单本教材，再评估多 PDF 批量汇总，不引入新的 OCR 服务。

### Q7：模型能力目录与任务路由

- [ ] 为模型注册 `provider`、`model`、显示名称、支持角色（生成/审核/陪练/视觉）、能力标签
  （JSON、视觉、数学、长上下文）、上下文上限、延迟级别、成本级别和回退模型。
- [ ] 增加轻量健康状态和最近一次失败原因；健康状态只影响候选筛选，不覆盖运行快照中的实际模型。
- [ ] 按任务能力筛选模型，而不是把大量供应商名称直接暴露给学生端；学生端只看到产品允许的陪练模型选项。
- [ ] 模型切换前后必须在固定评测集上比较正确率、结构质量、讲解质量、耗时、调用次数和回退率。

建议分支：`feat/model-capability-registry`。与 G1 `RunSnapshot` 配合，确保一次运行使用的配置可追溯。

### Q8：可恢复的批量处理工作流

- [ ] 长 PDF、多文件教材和整套重新审核使用任务 ID、独立进度、有限并发、限流、重试、取消和断点续跑。
- [ ] 记录每页/每题完成状态和幂等键，支持从失败位置继续，而不是重复整个批次。
- [ ] 任务结束生成成功/失败/隔离汇总，并提供失败原因和可重试入口；不把开发 Agent 的操作日志当作业务日志。
- [ ] 先复用 PostgreSQL `upload_jobs` 和单 Worker；只有测得吞吐不足时再评估 Redis 或其他队列。

建议分支：`feat/resumable-content-jobs`。该计划与 G3 后台任务一致，优先覆盖 OCR 和批量生成，不影响短请求。

### Q9：Agent 作为开发编排工具，而非生产运行时

- [ ] 保持生产流程由确定性路由、领域服务、Worker 和质量门禁执行；Agent 只用于开发期读报告、运行脚本、
  汇总进度和生成修复建议。
- [ ] 所有自动化脚本提供 `--count`、进度文件、限流和恢复参数，并输出结构化任务报告。
- [ ] 禁止让 Agent 直接修改学生掌握度、发布状态或数据库关键事实；这些状态必须经过 Schema 和领域服务。

这项原则不新增运行时依赖，也不构成引入 Multi-Agent、LangChain 或 LangGraph 的前置条件。

### 借鉴边界

- [ ] 不直接照搬一次处理数百本教材、固定十小时节流或每 N 本暂停等运营参数；参数应由本地基准和实际资源决定。
- [ ] 不因为截图显示模型在线就认定模型效果达标；在线状态、能力标签和离线质量评测必须分开记录。
- [ ] 不为个人 Demo 提前建设多租户、商业化、微服务 Control Plane 或复杂消息队列。

### 明确暂不纳入本路线

- [ ] Multi-Agent 矩阵、全局 LangGraph、独立 Agent 平台和 Tool Gateway。
- [ ] A Level 多学科题库、商业化会员/支付和生产级多租户服务。

这些方向已在上面的暂缓范围中记录，不作为质量闭环的前置依赖。

## 下一产品阶段：自主多模态智能导师

现有错题陪练已经具备一题一线程、确定性判题、受约束状态机、变式验证和复习闭环，但每轮回复仍主要由
固定阶段和提示层级驱动。下一阶段不改造成开放式 Agent，也不让模型直接写学习状态，而是在现有状态机
之上增加一个可解释的 `Tutor Turn Plan`：系统先判断本轮意图、误区和教学动作，再让模型负责自然表达。

### 阶段 A：可解释的单轮教学计划

- [x] 每轮生成结构化 `Tutor Turn Plan`，至少包含意图、判定、错误策略、教学动作、是否允许揭示答案、
  建议阶段和回复来源。
- [x] 六类错误原因映射到稳定的教学策略；自由文字可补充误区，但不得覆盖确定性判题结果。
- [x] 检测连续重复提示，最多升级一次提示策略；仍重复时使用可审计的确定性回退，避免模型调用循环。
- [x] 把计划摘要、模型 Provider、是否回退和阶段变化保存到消息动作中，便于复盘“为什么这样回复”。
- [x] 保持现有线程 API 向后兼容，并为策略选择、去重和状态不越权补充单元测试。

验收标准：相同题目和相同结构化输入得到稳定的教学计划；错误答案不会被模型改判为正确；重复请求提示时
教学动作会升级且单轮最多产生一次额外模型调用；旧线程仍可继续使用。

### 阶段 A.1：意图、误区与教学动作细化

- [x] 在服务端识别 `submit-answer`、`request-hint`、`request-explanation`、`check-step`、
  `challenge-answer`、`request-example`、`express-confusion` 和 `off-topic` 八类学生意图；按钮模式只作为
  证据之一，不作为唯一判断依据。
- [x] 模型在原有单次回复中输出当前误区假设、证据、置信度和是否需要确认，不额外串联一次诊断模型调用。
- [x] 低置信度、无证据或学生质疑标准答案时只追问确认，不把诊断写成已确认事实，也不推进到练习或验证。
- [x] 教学动作细分为条件提取、第一处错误检查、概念对比、补齐步骤、微型例子、说明依据、微型练习和自检；
  每轮只能执行一个动作。
- [x] 教学计划、回复上下文和持久化消息使用相同的意图/误区/动作契约，并保持旧线程响应字段兼容。

验收标准：常见中文口语和结构化作答能稳定得到预期意图；误区诊断必须有非空证据且置信度在 0～1；
低置信度诊断不会成为状态迁移依据；模型回复遵循选中的单一教学动作；本阶段不增加常规单轮模型调用次数。

### 阶段 B：统一多模态输入

- [ ] 定义统一 `TutorInput`，承载文字、结构化答案、题图裁切、画板快照和公式识别结果。
- [ ] 图片和画板先进入独立的理解适配器，产出“观察事实 + 置信度 + 证据区域”，不直接拼接为长文本。
- [ ] 低置信度结果要求学生确认；原图、识别文本和人工修正分层保存，避免覆盖原始证据。
- [ ] 为移动端上传、取消、压缩、失败重试和隐私提示补充交互与 Playwright 测试。

### 阶段 C：受约束工具与学习者画像

- [ ] 将判题、错误原因建议、提示选择、变式生成、掌握更新和复习安排暴露为显式工具契约。
- [ ] 模型只能提出工具调用建议；状态机、Schema 校验和领域服务决定是否执行。
- [ ] 建立按知识点聚合的学习者画像，仅保存错误模式、提示依赖和掌握证据，不保存无边界聊天历史。
- [ ] 回复上下文分为题目快照、线程摘要、最近必要消息和知识点画像，并分别设置长度与生命周期。

### 阶段 D：评测、观测与按信号升级

- [ ] 建立脱敏回放集，测量判题一致性、提示重复率、阶段越权率、首次有效提示率、耗时和调用次数。
- [ ] 为模型超时、回退、工具拒绝、图片理解低置信度和状态迁移记录稳定事件。
- [ ] 只有出现跨请求暂停恢复、复杂并行工具或两个以上流程重复编排时，才局部评估 LangGraph；
  LangChain、LangGraph 和多智能体都不是阶段 A 至 C 的前置依赖。

建议按 `feature/tutor-turn-planning`、`feature/multimodal-tutor-input`、
`feature/tutor-tools-profile` 和 `test/tutor-evaluation-suite` 拆分 PR，每个阶段可单独测试和回滚。

## 架构演进方向

```text
React / CDN
  → API Gateway / FastAPI
       ├─ PostgreSQL（关系数据 + Job Store）
       ├─ 对象存储
       └─ 单个后台 Worker（第一阶段）
              ├─ OCR / 题目生成与审校
              └─ 按指标升级 Redis / 多 Worker / TTS 预生成
```

在进程内状态外部化之前，不应简单增加 Uvicorn worker 数量；否则不同进程看到的模型选择、
任务状态和缓存可能不一致。
