## 为什么要有这次方向调整

项目此前同时并存 6 份路线图形状的文档，且反复修改：产品方向从“学生自学工具”改成
“服务一个学科组的教师”，又叠加“AI 工程学习优先于老师端功能”“AI 前沿实验线”等多次调整。
结果是每次改路线图都在悄悄回答“这个项目到底是什么”，而不是在细化同一个答案——多角色平台
（学生 / 教师 / 内容生产）三面等权重推进，路线图跟着堆叠，項目变得“四不像”。

这次调整不是又一次加法，而是一次明确的收敛：**选定一个主用户画像，让其余取舍都从它推导**。

## 主用户画像：个人自部署用户

主用户是**自部署使用者本人**——学生、家长或自学者，在自己的机器或自己控制的服务器上跑起来，
不经过学校采购、没有班级和多租户概念。这与此前“服务一个学科组、主用户是老师”的方向是**互斥**的
选择，不能都要：

- 教师画像需要班级管理、作业指派、多租户隔离、复核率/推翻率看板——这是学校 B 端 SaaS 的产品逻辑。
- 个人自部署画像不需要登录鉴权和班级概念，只需要单机好用、默认接本地模型、隐私可控。

选个人自部署画像的理由：

1. **这是项目真正的差异化空位**：中文教材 OCR + 中国 K12 数学错题场景，是同类开源教育项目
   （DeepTutor、OpenMAIC 等，均英文/通用/研究向）完全没有覆盖的空位，值得作为开源项目的核心叙事。
2. **和项目的本来目的一致**：项目对所有者而言的核心目的是学习和展示 AI 工程能力（`engineering-roadmap.md`
   的 AI 前沿实验线），而不是运营一个要交付给学科组的产品；个人自部署路径不需要为可能不存在的
   学校客户预先建设权限体系，能把精力留给 AI 能力本身。
3. **对外可信度更高**：一个能被任何人一条命令跑起来、且默认保护隐私（本地模型优先）的工具，
   比一个需要理解“教师/班级/作业”这套概念才能试用的平台，对开源社区更容易理解和采纳。

## 保留并作为主线的能力

- **AI 错题陪练**（`/mistakes`，旗舰功能）：拍照录题 → 错误原因归因 → 多轮陪练 → 变式掌握验证 →
  1/3/7 天复习，产品设计见 [`mistake-coach-plan.md`](mistake-coach-plan.md)。这是对外的核心叙事，
  是"个人 AI 学习工具"定位下最贴近日常使用场景的闭环。
- **学生学习空间**（`/learn`）：已发布互动试卷、错题本、进阶本、断网可恢复的学习会话。
- **AI 基建三件套**——这是项目对外最有辨识度的技术资产，继续维护并作为技术叙事的核心：
  - **Run Snapshot**：不可变运行快照，固定模型/Prompt/Schema/校验器版本，任何一次 AI 处理都可追溯。
  - **PostgreSQL Job Store + Worker**：长任务的租约、幂等、有限重试和可恢复执行。
  - **离线评测 + Judge 报告**：确定性回放、Badcase 登记簿、LLM-as-Judge 讲解质量评审，
    区分"该用确定性判断"和"该用模型评审"的场景。
  详见 [`runtime-governance-plan.md`](runtime-governance-plan.md)。
- **语音三级回退**（Azure Speech → Qwen3-TTS → 浏览器 Web Speech）：本地模型优先的设计天然契合
  自部署用户对隐私和离线的需求，继续保留。
- **内容生产工作台**（`/studio`）：从"对外产品面之一"降级为**内部/进阶工具**——自部署用户或
  贡献者用它把自己的教材变成题库，不再是首页三大入口之一，不再围绕它做面向"生产环境"的复杂度
  （批次熔断、依赖自检等仍按 `engineering-roadmap.md` 的技术优先级推进，但目的是让自部署更可靠，
  不是让它成为多用户生产服务）。

## 已归档、不再是产品主线

- **教师工作台**（`/teacher`）：班级、成员、作业指派、掌握分布看板、教师 override、复核率/推翻率
  埋点。这是为学校 B 端场景设计的一整套功能，与个人自部署定位冲突。**不删除、不回滚**已完成的代码
  和数据模型，但不再新增功能。相关设计文档移入 [`archive/product-roadmap-teacher-era.md`](archive/product-roadmap-teacher-era.md)。
- **学科组试用验证方法论**（原 `pilot-plan.md`）：复核率/推翻率目标区间、失败判据、试用前后访谈——
  这套方法论是为"要不要做成学校产品"这个决策设计的，决策已经改变，方法论随之归档，见
  [`archive/pilot-plan.md`](archive/pilot-plan.md)。方法论本身（写死失败判据、只记录行为不征求意见）
  仍值得在未来任何需要真实用户验证的场合复用。
- **多租户、登录鉴权、7×24 SLA、高可用与公网运营**：继续暂缓，理由不变——个人自部署单用户场景
  本来就不需要这些；如果未来真的有人需要多用户部署，届时再重新论证，不预先建设。

## 已论证但未排期（不分主用户画像，继续保留）

以下条目此前记录在已归档的 `product-roadmap.md` 中，与教师/学校场景无关，对个人自部署场景同样
成立，保留作为待触发的候选项（详见归档文档原文）：

- 标准试卷/讲义导出（Word）——自学者也需要可打印的练习材料。
- 教材原文定位与注释模型、教材版本漂移检测——自部署用户自己导入教材同样会遇到版本更新问题。
- 拍照单次多模态调用（收缩现有多阶段 OCR 流水线）、题图视觉复审闭环——直接提升错题陪练的输入质量。
- 知识点依赖图（从教材目录/课标结构派生，不用模型猜）——见下一节，与 RAG 方向合并考虑。

## 下一步方向：AI 前沿实验线（追踪最新 AI 方向的核心）

这是项目"简历/学习价值"真正的着力点，继续按 [`engineering-roadmap.md`](engineering-roadmap.md) 的
优先顺序推进，其中与本次方向调整关系最大的两项：

1. **检索增强 Tutor（RAG）**：当前项目在"教材 → 结构化题目"这条链路上很扎实，但错题陪练本身没有
   知识检索层。已有 PostgreSQL 全文检索第一版；下一步主动对照混合检索、reranker 和 embedding，
   决定是否需要向量索引。这是对外最容易被识别的"当前 AI 方向"关键词之一，也是同类参考项目
   （DeepTutor 的多引擎 RAG、OpenMAIC 的 `lib/rag`）都在做、而 dotty-tutor 目前缺的一环。
2. **Agent 轨迹与工具编排的隔离实验**：现有陪练状态机是确定性状态机 + 受约束 `ToolProposal`，
   刻意没有引入 LangGraph 等编排框架进生产链路。继续保持这个边界，但在隔离实验中主动比较图式编排
   （参考 OpenMAIC 的 director graph 模式）能否让多轮陪练的"该不该继续追问 / 该不该升级提示"这类
   决策更可解释，而不是直接替换生产状态机。

不属于本次方向调整范围、原文不变的技术优先级（T0 正确性、T1 可复现性、T2 可靠性、T3 实验能力）
继续见 [`engineering-roadmap.md`](engineering-roadmap.md)。

## 开源化待办（新增，服务于"个人自部署"定位）

- **Turnkey 自部署体验**：验证并保证 `docker compose up` 默认路径在零 API key、零外部账号的情况下
  能跑通完整的错题陪练闭环（默认接本地 Ollama）；这是自部署用户的第一道门槛，需要专门验证，
  不能假设现有 `.env.docker.example` 默认值已经做到。
- **文档双语化**：面向自部署/开源受众，`README.md` 补充英文版本，降低国际受众的了解成本。
- **路线图讨论迁移到 GitHub Issues**：不再用仓库内文档承载"接下来做什么"的讨论，参考 OpenMAIC/
  DeepTutor 的做法，把候选方向放到 Issues 里，让潜在贡献者可以直接参与讨论。

## 产品验收原则（延续）

1. 先验证个人用户能否独立完成"录入错题 → 陪练 → 验证掌握"这条最小闭环，再增加模型或页面能力。
2. 任何 AI 功能都必须有确定性状态机、错误回退和可重复测试。
3. 新能力（RAG、编排实验、新题型）必须是独立实验，不阻塞现有错题和复习闭环，也不绕过现有状态机
   直接写入学生学习状态。
