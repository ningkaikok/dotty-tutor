# AI 错题陪练产品规划

本文定义 Dotty Tutor 在保留教材数字化能力的前提下，扩展个人错题陪练产品的目标、边界、
复用策略和分阶段交付计划。错题陪练与内容生产共用一个仓库和技术底座，但位于独立学生空间，
避免把上传、OCR、模型和审校配置暴露给学生。

## 产品定位

目标用户是小学至高中及中职的个人学生，首个可用版本聚焦**初中数学**。产品强调三件事：

- **轻**：移动端网页直接使用，后续可通过二维码在微信内打开，不要求安装 App。
- **准**：错题落到具体教材章节、知识点和错误原因，允许学生确认和修正 AI 结果。
- **闭环**：不止保存错题，还要通过多轮陪练、变式验证和复习计划确认学生真正掌握。

Dotty Tutor 的总定位调整为“个人 AI 学习工具”，包含两个角色入口和一个学生子产品：

| 入口 | 路径 | 主要任务 | 当前状态 |
| --- | --- | --- | --- |
| 内容生产工作台 | `/studio` | 教材导入、结构化出题、质量复核和互动预览 | 已可用 |
| 学生学习空间 · AI 错题陪练 | `/mistakes` | 错题录入、诊断、多轮辅导、掌握验证和复习 | 阶段四闭环已完成 |

内容生产统一使用 `/studio`。

## 核心用户闭环

```mermaid
flowchart LR
  Capture["拍照录入错题"] --> Confirm["确认题目与原答案"]
  Confirm --> Classify["匹配章节、知识点和错误原因"]
  Classify --> Tutor["单题智能体多轮陪练"]
  Tutor --> Verify["生成不同变式验证"]
  Verify -->|"验证题答对 1 次"| Mastered["进入进阶本"]
  Verify -->|"仍未掌握"| Tutor
  Mastered --> Review["1 / 3 / 7 天复习"]
  Review --> Verify
```

错误原因是后续策略的核心数据，不作为可有可无的标签。第一版使用以下稳定枚举：

| 标识 | 中文 | 后续策略示例 |
| --- | --- | --- |
| `concept` | 概念不清 | 先解释定义，再做基础辨析 |
| `reading` | 审题错误 | 让学生标出条件与问题 |
| `calculation` | 计算失误 | 生成同类型分步计算练习 |
| `missing_step` | 步骤遗漏 | 要求补齐推导或证明链 |
| `unknown` | 完全不会 | 从前置知识开始逐级提升 |
| `careless` | 粗心大意 | 增加检查清单和限时复核 |

## 单题智能体设计

每道错题进入陪练页后拥有独立线程，不把一次模型生成当成完整辅导。状态机为：

```text
diagnose → explain → practice → verify → mastered
               ↑         │          │
               └─────────┴──────────┘
```

智能体根据学生的文字、选项、公式、图片或画板输入决定下一步，并通过受约束工具写入业务数据：

- `evaluate_answer`：调用确定性判题，模型不自行宣布对错。
- `diagnose_error_reason`：生成可由学生确认的错误原因。
- `explain_misconception`：按当前误区生成短解释。
- `select_next_hint`：只返回当前所需的一层提示。
- `generate_practice_question`：生成同知识点、不同表述的练习。
- `update_mastery`：根据验证结果更新掌握状态。
- `schedule_review`：创建后续复习任务。

达到“已掌握”需要完成一道验证题并答对。答错时保留同一道题，允许学生修改后重新提交，避免不断生成
新题掩盖原来的误区。MVP 的复习间隔为 1、3、7 天；后续再基于题目难度和历史表现调整。

验证题生成目前是同步调用 `generate_lesson` 的模型请求，首次生成耗时主要来自 Codex CLI/Ollama
启动、网络或本地模型冷启动，而不是确定性判题。服务端会在生成前复用已有验证题，浏览器重复点击、刷新或
从 `practice` 推进到 `verify` 都不会再次触发模型；因此一次真实模型调用对应一题，后续错误重提交流程不再
等待生成。若首次生成仍较慢，应优先检查生成模型选择、模型进程健康状态和 `model.generation.*` 日志，异步
任务队列属于后续部署优化，不在个人 Demo 的同步闭环中引入。

## 代码复用边界

### 直接复用

- OCR 与题图提取：`apps/api/infrastructure/runtime/ocr_runtime.py`。
- 结构化生成：`apps/api/infrastructure/runtime/model_runtime.py`、`apps/api/domain/questions/pipeline.py`。
- 题型与答案契约：`apps/api/domain/questions/contracts.py`。
- 确定性判题：`apps/api/answer_evaluator.py`。
- 审校与质量门禁：`apps/api/infrastructure/runtime/review_runtime.py`。
- 应用、日志、PostgreSQL、Docker 与 Playwright 基础设施。
- 前端公式、题图和结构化作答组件。

### 适配后复用

- `apps/api/application/services/tutor_engine.py`：从单次 Help 扩展为带线程状态的策略引擎。
- `apps/api/persistence/`：按错题、消息和复习任务拆分 Store，不继续堆积单文件职责。
- `apps/web/src/components/PracticeWorkspace.tsx`：抽出可在错题陪练中复用的题目与答案区域。
- `apps/api/api/routers/learning_routes.py`：保留掌握度逻辑，增加验证次数和复习计划。

### 学生入口不直接复用

- 大 PDF 批处理、模型/OCR 选择器、审校产物和重新生成按钮。
- 默认四步课程播放器。它可作为深度讲解资源，但不是每次对话的固定流程。
- 任何暴露模型、提示词或内部质量信息的开发调试界面。

## 目标架构

前端已按产品域拆分，同时把真正通用的题目组件放入共享层：

```text
apps/web/src/
  apps/
    home/                 # 角色入口
    textbook/             # 内容生产与互动预览
    mistake/              # 错题陪练
  components/             # 通用题目、公式、画板与反馈组件
  lesson/                 # 可编程课程播放器
  api/                    # 教材、错题、辅导、运行时和学习 API
  types/                  # 对应领域类型
  api/ types/             # 按领域拆分的请求与类型入口
```

后端保持模块化单体，业务域使用明确文件边界，避免把新接口写入 `apps/api/app.py`：

```text
apps/api/
  mistake_*.py            # 错题录入、归类和仓储
  tutoring_*.py           # 线程契约、路由和消息仓储
  application/services/stateful_tutor.py # 状态机与有限上下文
  api/routers/learning_routes.py         # 教材学习掌握度；错题验证和复习使用独立路由
```

计划新增的核心数据模型：

- `mistake_items`：题目快照、学生原答案、知识点、错误原因和状态。
- `tutor_threads`：一题一线程，记录当前辅导阶段与摘要。
- `tutor_messages`：学生输入、助手输出、结构化动作和模型运行信息。
- `review_tasks`：复习时间、题目来源、完成状态和验证结果。

线程只保存业务所需的结构化上下文和摘要，不无限重放全部消息，控制延迟与 token 成本。

## 分阶段交付

### 第一阶段：角色与产品入口（已完成）

- 根路径展示学生学习与内容生产两个角色入口。
- `/studio` 承载教材上传、生成和互动预览。
- `/learn` 是学生学习空间，汇总互动试卷、错题与复习入口；`/mistakes` 只承载错题闭环。
- 拆分原有大体积 `App.tsx`，根组件只负责路由，教材状态归入产品域组件。
- 增加入口和直接路由的 Playwright 回归测试。

### 第二阶段：错题录入与确认（已完成）

- 单张图片上传、裁切与 OCR。
- 展示题干、公式、题图和学生原答案，允许手动修正。
- 匹配教材章节与知识点，记录可修正的错误原因。
- 新增 `mistake_items` 表和错题本列表。

当前实现还包括浏览器端裁切、错题原图持久化、六类错误原因、归档操作和直接确认页路由。
归档是软删除：题目、错误原因和学习证据仍保留，默认列表会隐藏；归档时会清理该题的
陪练线程和消息，恢复后从新的对话开始，避免继续使用已经过期的教学上下文。
学生确认“准备好了”后会确定性地进入 `practice`，并自动生成一道不同于原题的验证题；
答错时可在原题上重新提交，答对一次即可确定性地推进到 `verify` 并标记掌握。验证题区域
独立记录作答，避免把答案误当成自由对话消息。前端将 `diagnose`/`explain` 合并显示为
“理解错因”，并把后续两个后端阶段显示为“变式练习”和“掌握验证”。
章节与知识点由模型给出候选并由学生确认；精确关联已导入教材知识树仍属于后续的数据治理工作。

### 第三阶段：有状态单题陪练（已完成）

- 新增线程和消息模型、线程 API 与辅导状态机。
- 支持文字和已有结构化作答输入，逐步接入图片与画板。
- 确定性判题负责结果，模型负责诊断、提示与追问。
- 使用摘要和有限上下文控制多轮成本。

当前实现为每道已确认错题创建唯一线程，原子保存每轮学生和助手消息，并在 `diagnose`、`explain`、
`practice`、`verify` 四个状态间推进。选择、判断、多选、填空、数值和画线输入直接复用已有作答组件；
自由文字继续交给模型引导。原题纠错完成后进入 `practice`，首道变式题答对才进入 `verify`，不会绕过变式验证直接标记掌握。

### 第四阶段：掌握验证与复习

- 按错误原因生成不同策略的变式题。（已完成）
- 验证题答对一次后从错题本迁移到进阶本。（已完成）
- 建立 1、3、7 天复习任务和学习进度页。（已完成）

前两步已将验证题作为独立练习记录保存，而不是混入自由对话消息。生成服务根据六类错误原因选择策略；
验证题只生成一次，重复请求复用已保存题目，答错允许更新同一条作答证据，答对后记录原子迁移为
`mastered`。系统只接受可确定性判题的选择、多选、填空和数值题。迁移时幂等创建第 1、3、7 天任务；每项
任务保存独立迁移题和一次作答结果，进度页汇总掌握率、到期任务、完成数、复习正确率和知识点状态。

### 第五阶段：微信移动体验

- 完成小屏、触控、拍照权限与弱网体验。
- 二维码入口和微信内浏览器兼容性验证。
- 在身份体系完成前继续使用受控演示数据，不采集真实学生隐私。

### 第六阶段：质量与演示

- 补齐关键路径 Playwright、真实 PostgreSQL 集成测试与模型评测集。
- 增加首屏、响应耗时、模型失败和学习闭环指标。
- 准备可重复运行、无需临场生成全部内容的演示数据。

### 第七阶段：自主多模态智能导师

本阶段不是移除现有状态机，也不是让大模型自由决定学生是否掌握，而是把当前“状态 + 提示层级”升级为
“证据 → 教学计划 → 自然回复 → 受约束动作”。完整分期和验收标准见
[路线图中的自主多模态智能导师计划](roadmap.md#下一产品阶段自主多模态智能导师)。

第一批实现已完成以下最小增量：

1. 生成可持久化、可测试的单轮教学计划，明确本轮意图、错误策略和教学动作。
2. 复用现有确定性判题和状态机，模型只能解释与追问，不能覆盖判题或直接标记掌握。
3. 对连续相似提示进行有上限的策略升级，记录模型、回退与去重原因。
4. 固定线程 API 和现有学生页面的当前契约，为后续图片、画板和手写公式输入预留统一结构。

当前单轮调用链如下：

```mermaid
flowchart LR
  Input["学生文字或结构化作答"] --> Judge["确定性判题"]
  Judge --> Plan["Tutor Turn Plan"]
  Profile["错误原因与当前阶段"] --> Plan
  Plan --> Reply["模型或预制引导卡负责表达"]
  Reply --> Dedupe["相似提示检测：最多重试一次"]
  Dedupe --> Persist["原子保存消息、计划与模型审计"]
  Plan --> Guard["受约束状态迁移"]
  Judge --> Guard
  Guard --> Persist
```

其中确定性判题是阶段推进的唯一正确性依据。模型生成的 `correct` 只能作为辅导线索，不能让线程跳过
练习或验证；提示重试达到上限后使用确定性问题回退，不会继续递归调用模型。

在这一基础上，陪练已进一步细化三项决策：

- 服务端根据结构化作答、操作模式和明确口语识别提交答案、请求提示、请求解释、检查步骤、质疑答案、
  请求例子、表达困惑和无关输入八类意图，不额外调用分类模型。
- 模型在原有一次结构化回复中提出误区假设、证据和置信度。后端会核对证据是否与学生本轮原文重合；
  无证据、证据不匹配或置信度低于 0.65 时只能追问确认，不能将假设写成已确认误区。
- 每轮从条件提取、第一处错误检查、概念对比、补齐步骤、微型例子、说明依据、微型练习和自检中选择
  一个教学动作。模型生成前锁定动作；只有发现诊断证据不足时允许改为追问确认，并记录调整原因。

普通回复仍只使用一次模型调用。只有连续提示高度相似时，才沿用已有的最多一次有界重试。

多模态输入在下一批接入：图片与画板首先转换为带置信度的观察事实，学生确认后才进入教学决策。这样可以
避免把 OCR 或视觉模型的猜测当成学生真实思路，也能让错误结果被定位、重试和审计。

建议对应分支：

```text
feature/dual-product-entry
feature/mistake-capture
feature/stateful-tutor-thread
feature/mastery-review-loop
feature/mobile-mistake-experience
test/mistake-coach-e2e
```

## 性能和成本目标

- 移动端入口可交互时间小于 2 秒。
- 确定性判题响应小于 500 ms。
- 智能体文本回复目标 P50 小于 5 秒、P95 小于 10 秒。
- TTS、动画和知识点讲解优先缓存或异步预生成，不阻塞第一条文字反馈。
- 每轮只携带题目快照、状态摘要和最近必要消息，记录 provider、耗时、token 与回退原因。

## MVP 明确不做

- 同时覆盖全部学段、学科和教材版本。
- 每道题实时生成讲解视频。
- 微信登录、支付、教师后台和班级管理。
- 复杂手写公式识别和任意画板语义理解。
- 多智能体协作、微服务拆分或 Kubernetes。
- 无人工确认地自动生成整本教材知识树。

这些能力不是永远不做，而是不应阻塞“录入一题—陪练—验证掌握”这一条最小闭环。
